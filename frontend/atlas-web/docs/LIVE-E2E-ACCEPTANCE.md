# Live Atlas E2E acceptance contract

Status on 2026-10-08: **NOT_RUN — backend source, approved DTO and independent authenticated environments are absent.** This is an acceptance plan, not a set of fabricated results. Frontend protocol peers cannot certify these journeys. Use `SRS-ADR-CONFORMANCE.md` and `requirements-traceability.json` for the complete requirement mapping.

## Test environment and proof

Backend/QA owners must supply an immutable backend image SHA and migration version; Java/Spring/Modulith modules; Temporal; PostgreSQL with RLS; Redis; Qdrant; S3; hardened sandbox workers; and test GitHub App installation plus synthetic LLM adapters. Test Compose has the seven users from SRS13.2 (six roles plus custom auditor), two strongly isolated orgs, seeded key pools and exhausted-budget org, locked/conflicted/draft specs, active/proposed workflows, gates and tasks in every required state. Production Compose must start empty with migrations/OAuth bootstrap and no mock services or seeded credentials. Validate these modes separately.

Workspace and Observer use independent HTTPS origins and audiences, host-only Secure cookies, separate auth/storage/router and current frontend release build ID. Backend rejects every cross-tenant/API/WS/object/vector access and independently enforces RBAC, entitlements and quota. No PAT replaces the required GitHub App. Do not put keys/cookies/raw customer source in exported evidence.

Each executed step records UTC start/end, actor ID, audience, org/workspace/project, resource ID, expected/result revision, operation ID/idempotency key, canonical input fingerprint, server acknowledgement and matching effect readback, correlated audit/hash-chain record, backend/worker/Temporal activity IDs, and sanitized artifact SHA/path. A 200/Accepted, screenshot or client journal is not a business effect. Missing/mismatched evidence fails acceptance. After timeout/network loss, status GET reconciles the same operation ID; never POST again automatically. Server replay must deduplicate and conflicting reuse must fail.

Tests with destructive crash/deletion/merge actions run only in explicitly scoped disposable backend fixtures. This continuation performs no such remote action. Existing UI approval and deployment authorization gates remain in force.

## Release and acceptance sequence

1. Resolve C01–C07 and approve API/enum/config mapping; backend implementation passes its own architecture, RLS/RBAC/entitlement, provider/webhook contracts, Temporal replay/recovery and sandbox security suites. Scan dependencies, produce SBOM and scan immutable backend images, per ADR38–39.
2. Complete UI review. After explicit deployment authorization, release both independent frontend hosts and pinned backend images. Follow `DEPLOY-ACCEPTANCE.md`; a missing second host or mismatched build ID is a failure.
3. Run Test Compose journeys J0–J7/O1 with every negative/recovery branch. Measure NFR timings with throughput/network/device/clock basis. Run all 27 EX rows and 40 BR rows from the registry; no broad label covers a missing individual case.
4. Run read-only staging delivery/header/build checks on both HTTPS origins in three engines, then the authorized live business journeys. Retain raw errors and reruns separately. Manual NVDA/VoiceOver remains required; axe does not certify screen-reader behavior.
5. Obtain product/security acceptance from concrete evidence before manual production approval. Any missing required case, blocked conflict or unverified effect retains NOT_ACCEPTED.
